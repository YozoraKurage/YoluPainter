# タイル合成とブラシの GPU プレビュー

`GpuPainter` は wgpu 30 の compute で、`yolu-core` の平坦なレイヤー文書をタイルごとに合成します。26 合成モード、レイヤーの不透明度、表示、チャンネル、クリッピングを扱います。RGB の色空間を変換せず、straight RGBA8 をレイヤーごとに半段切り上げで丸めます。元の CPU タイルは読み取るだけです。保存・Undo の正本には常に `yolu-core` を使ってください。

```rust
use yolu_core::{Channel, Document, TileCoord};
use yolu_gpu::{Compositor, Options};
let doc = Document::new(128, 128).unwrap();
let mut compositor = Compositor::new(Options::default());
let result = compositor.composite_tiles(&doc, Channel::Color, &[TileCoord::new(0, 0)]).unwrap();
assert!(result.is_current(&doc));
// GPU が使えなければ CPU の結果と fallback_reason() の理由が得られる。
```

`Document::changed_tiles(channel, serial)` の一覧を `composite_tiles` に渡すと、そのタイルだけを合成します。空になったタイルも透明な結果を返します。端の部分タイルは `TileResult::rect` の幅と高さに切り詰めます。行は左下から上へ並びます。キャッシュは呼び手が所有し、文書・チャンネルの切り替えでは破棄してください。同じ ID を持つ文書を読み直したときも破棄します。`is_current` は同一の文書を編集し続けている間の ID・revision 照合です。

`brush_dabs` はストローク開始前の矩形と補間済みの `Dab` 一覧を受け取り、丸い筆先の smoothstep、硬さ、筆圧、流量、不透明度の天井、消しゴムを計算します。座標は渡した矩形の左下からの画素座標です。同じストロークのダブをまとめて渡してください。複数呼び出しをまたぐ覆いの蓄積や入力点の補間は行いません。取消では結果を捨て、正本の描画・Undo は core のストロークで行います。ブラシのアンチエイリアス（`BrushSettings::anti_alias`）が「なし」以外の設定は、この経路では描けないので理由つきで断ります（縁の帯と小さなダブの濃さは core のストロークだけが持ちます）。ブラシの色の混ぜ（厚塗り）はこの経路に持ち込みません。混ぜは打点ごとに下の画素を読んで筆の荷（ブラシが持つ色）を更新するので、丸い筆先の覆いと色だけを返すこの経路で計算すると、core の結果とずれます（[ブラシ](../../docs/BRUSH.md#色の混ぜ厚塗り)）。透明画素の RGB は入力コピーと無描画で保持し、消しゴムでアルファが 0 になったときは core と同じく RGBA を 0 にします。

## 常駐キャッシュと表示テクスチャ

`ResidentCompositor` は入力のレイヤータイルを GPU に常駐させ、合成結果を表示用の `Rgba8Unorm` テクスチャに保持します。`update` は `Document::changed_tiles` の世代を追い、影響を受ける座標だけを再合成します。その座標の各レイヤーを CPU の照合用コピーと完全比較して、実際に変わったレイヤーのタイルだけを転送します。転送するタイル・命令の並び・調整の表・束ごとの定数は 1 本の並びに詰め、GPU 側の一時のバッファへ `write_buffer` 1 回で書いて GPU の中で行き先へ写します（書き込みの呼びが重いデバイスで、タイルごとの書き込みが積み重なるのを避けるため）。書き込みの回数は `UpdateStats::transfers` で、普通は 1 です。1 回に溜める量は予算の空きの 1/3（64 MiB まで）が上限で、超える前と、まだ流していない束が読むタイルを追い出す前には、そこまでを流します（`ResidentOptions::transfer_limit_bytes` で試験が固い上限を置けます）。不透明度・合成モードなど画素を変えない変更では、入力の再転送が不要です。ハッシュ衝突に依存しない代わりに、入力と同量の CPU コピーを持ちます。

```rust
use yolu_core::{Channel, Document};
use yolu_gpu::{ResidentCompositor, ResidentOptions};
let doc = Document::new(256, 256).unwrap();
let mut gpu = ResidentCompositor::new(ResidentOptions::default())?;
let stats = gpu.update(&doc, Channel::Color)?;
let display = gpu.display()?;
// display.texture / display.view を表示に使う。行は左下から。保存は core の正本から行う。
assert_eq!(display.revision, doc.revision());
// 必要なときだけ任意の矩形を読み戻す。
let request = gpu.request_readback(doc.bounds())?;
let pixels = gpu.finish_readback(request)?;
# Ok::<(), yolu_gpu::GpuError>(())
```

表示テクスチャは借用で返します。次の更新で内容が変わるため、古い世代のスナップショットとして保持しないでください。文書 ID・寸法・チャンネルの変更で常駐コピーを破棄します。同じ ID の文書を再読み込みするときは `reset()` を明示的に呼んでください。レイヤーの追加・削除・順序変更・入れ子・マスク・塗りつぶしの値、取消・Undo・Redo も変更記録のタイルから反映します（初めて・文書やチャンネルが替わったときだけ全部を合成します）。`GpuPainter` の既存の読み戻し API とブラシは引き続き利用できます。

### 合成できる文書と、断る文書

合成するレイヤーの並びは `plan.rs` の 1 か所で作り、`GpuPainter::composite_tiles` と `ResidentCompositor` が同じものを使います。`yolu-core` の CPU の計画と同じ規則（兄弟ごとのクリッピングの組、見えない下地は組ごと落とす、グループは中身の計画）で、そのチャンネルの不透明度と合成モード（`ChannelBlend`）を使います。計画は平らな命令の並びで、シェーダーが画素ごとに先頭から 1 回だけ流します（再帰しません）。結果と、クリッピングの組の値のレジスタに、入れ子のグループが退避する小さな積み（結果と組の値を 1 語ずつ）を持ちます。作業のテクスチャも、グループごとの追加の合成の段も持たないので、予算に足すのは命令の並びと調整の表だけです。

- 合成できるもの: ラスターレイヤー、塗りつぶしレイヤー（チャンネルごとの値）、ラスターマスク（有効・反転・濃度）、26 の合成モード、チャンネルごとの合成、クリッピング、グループ（通過で不透明度 1・マスクが効かないものは中身を下へそのまま重ねるのと同じなので平らにします。そのほか、通過で不透明度が 1 でない・マスクが効くものは下とフェードし、通過でないもの・クリッピングされるもの・クリッピングの下地になるものは中身を透明から合成して重ねます）、調整レイヤー（反転・レベル補正・色相/彩度・グラデーションマップ・トーンカーブ・カラーバランス・明るさ/コントラスト・2 値化・ポスタリゼーション。クリッピングされた調整も、グループの中の調整も）、法線の種類のチャンネル（単位ベクトルの重ね・クリッピング・フェード。Overlay は RNM、ほかのモードは置き換え）、効果（有効なフィルター・Generator・塗りつぶしのグラデーションと投影・マスクのフィルター）のある文書。
- 断るもの（`supports` と `update` が `Unsupported` の理由を返します）: 文書にないチャンネル、シェーダーの積みに収まらない深さのグループの入れ子（独立して合成するグループで 32 段、通過のグループで 64 段。文書の入れ子の上限は 64 段）。黙って違う絵にせず、呼び手が CPU の合成を使います。`update` は断っても GPU を失敗扱いにしません（文書が合成できる形に戻れば続けて使えます）。`Compositor` は断った呼び出しだけ CPU で合成し、GPU は捨てません。

調整は、成分ごとに決まる式（レベル補正・トーンカーブ・明るさ/コントラスト）は CPU の `apply_in` に灰色の画素を通した結果を 256 の表にして上げ（成分が独立なので、R・G・B の表が灰色 1 本の探りで全部引けます。CPU とバイトまで同じ）、グラデーションマップは CPU と同じ式で作った輝度 → 色の表を上げます。反転・2 値化・ポスタリゼーションはシェーダーの整数の式で、CPU とバイトまで同じです。色相/彩度とカラーバランスだけシェーダーの f32 の式で、f32 と f64 の丸めの境で 1 バイトずれ得ます（色相・彩度・カラー・輝度や除算のように、上の色の彩度や値の小ささで結果が大きく動くモードで重ねると、その差が増えます）。

効果の計算そのものは CPU（`yolu-core` の評価）のままです。評価した出力は `Document::layer_output_into`・`mask_output_into`（文書の評価のキャッシュ。CPU の合成と同じ評価の道）から、束のタイルを含む矩形をまとめて読み、タイルとして常駐に上げます（タイルごとに頼むと、評価がブロックを 1 つずつ直列に評価するため）。出力が全部 0 のタイルは常駐させません。変更の記録（ぼかしの半径の分や、全体の統計を使う段・Anchor の読み手を含む）は core が持つので、更新は変わったタイルだけを評価して上げ直します。

シェーダーは、使わない文書に積み・調整の式・法線の式を持たせない形（`plan.rs` の `Variant`）で、使う形ごとに初めて要るときに作ります。画素ごとの私的な積みと調整の式が入っていると、グループも調整も無い文書の合成まで遅くなるためです（ソフトウェアの GPU の計測で 3 倍）。

レイヤーの画素のない所（無いタイル）は常駐させず、作業域を 0 で埋めます。見えないレイヤー（隠す・不透明度 0・チャンネルが無効）は並びに入れず、画素も上げません。疎な文書で全タイルぶんの GPU バッファを作らないための扱いです。

### 全部が常駐するかの見積もり

`resident_requirements(doc, channel, options, limits)` は、描いたタイル（レイヤーとマスクの、無いタイルを除く。評価の出力を持つレイヤーは、全部を評価するまで描いたタイルの数が決まらないので、持ち得る数の上限: 塗りつぶし・Generator・画像の投影はキャンバス全体、ぼかしは元のタイルを半径の分だけ広げた範囲）を全部常駐させるのに要る量を、GPU に触れずに見積もります。表示のテクスチャ・作業域・転送の余裕（`fixed_bytes`）と、タイルの GPU コピーと同量の CPU コピー（`tile_bytes`）で、`update` が数える `UpdateStats::resident_bytes` と同じ式です（全タイルが常駐したとき一致します。評価の出力を持つレイヤーは、実際に常駐する量が見積もり以下になります）。合計が予算を超える文書は、追い出しながらでも合成できますが、レイヤーの不透明度や合成モードのような全面の変更のたびに全タイルを上げ直すので遅くなります（4096²・4 レイヤーが全面で、コンテナの実 GPU では CPU の 3 倍ほど、ソフトウェアの GPU では 4.5 倍ほどの時間）。呼び手はこの見積もりで、CPU の合成を選べます。デバイスの上限を超える大きさ・GPU が扱えない文書は Err です。

### アプリのデバイスで動かす・乗算済みの表示

`GpuPainter::from_device(info, device, queue, options)` は、呼び手が持つ wgpu のデバイスとキューで作ります。egui の描画と同じデバイスを渡すと、`Display::texture` を読み戻さずにネイティブのテクスチャとして見せられます。compute や storage の上限が足りないデバイス（WebGL2 並みの上限など）は、パイプラインを作る段階で理由つきのエラーになります。デバイスの上限（`max_texture_dimension_2d`、ストレージバッファの束縛の大きさ）に収まらない文書も理由つきで断ります。
`device_can_composite(&Limits)` は、そのデバイスの上限で合成できるか（合成とダブの束ねのストレージバッファ 7 つ・ストレージテクスチャ 1 つ・大きさ 64 のワークグループ〔compute の実行の単位〕）を、文書を見る前に答えます。egui-wgpu は OpenGL のとき WebGL2 並みの上限でデバイスを作るので、そこで足りなければ呼び手は合成を試さずに CPU を選べます。

`ResidentOptions::premultiplied_display` を立てると、表示のテクスチャを乗算済みのアルファで書きます。式は egui の `Color32::from_rgba_unmultiplied` と同じ整数の式（アルファ 0 は全部 0、255 はそのまま、ほかは `p = v × a + 128; (p + (p >> 8)) >> 8`）で、straight の表示から CPU で変換した値とバイトまで一致します。読み戻しも乗算済みの値になります。

同じ照合（マスク・塗りつぶし・チャンネルごとの合成・クリッピング・通過のグループ・取消・並べ替え・削除）は、`cargo run --release -p yolu-gpu --example canvas_check` でメインスレッドから、使えるアダプターに対して動かせます（Mesa の d3d12 経由の OpenGL のように、テストの子スレッドでデバイスを作ると落ちる環境のため）。アダプター名を併せて記録してください。

### 表示の許し（GPU と CPU の差）

レイヤーごとに半段切り上げで RGBA8 に丸める式は CPU と同じで、どちらも f32 で計算しますが、シェーダーの演算の丸め（積和へのまとめなど）は CPU の式（積和へまとめない）と同じとは限らないため、1 段ごとに最大 1 の差が出ることがあります。重なったレイヤーの差は次の段の式で増幅され（Overlay・HardLight は最大 2 倍、ColorDodge・ColorBurn・VividLight・Divide はそれ以上）、マスク・塗りつぶし・グループ・チャンネルごとの合成を重ねた試験の文書（`tests/canvas.rs`）では 2 以内でした。任意のレイヤー数・モードでの上限は保証しません。この差は表示だけで、保存・書き出し・3D の値は常に CPU の正本から作ります。

### 常駐予算と読み戻しの寿命

既定の常駐予算は 768 MiB。表示テクスチャ、入力の GPU コピーと同量の CPU コピー、作業バッファ、束ごとの転送用余裕を数えます。消えたレイヤーに加えて、隠したレイヤー・不透明度 0・無効にしたマスクなど合成の計画から外れた面のタイルも常駐から手放し、戻したときは変更記録のタイルを上げ直します。上限に達すると、最後に使用した時刻が古いレイヤータイルから追い出します。表示と最小 1 束すら入らない予算は、理由付きで拒否します。`UpdateStats` で更新数・転送数/バイト・ヒット数・追い出し数・保持予約量を確認できます。CPU のコンテナ管理領域、シェーダー、ドライバーの内部プール、呼び手が持つ CPU の読み戻し結果は対象外です。

更新は最大 16 タイル（設定可能、1〜64）ずつ処理します。常駐入力から作業域への GPU 内コピーを行い、入力とは別の表示テクスチャに書き込みます。画素の読み戻しはありませんが、転送用メモリの寿命を区切るため束ごとに GPU の処理完了を待ちます。フレームをまたいで表示更新を非同期に重ねる実装ではありません。

読み戻しには別の既定 64 MiB の予算があります。256 バイトに揃えた行幅で、未完了または未取得の要求のバッファを合計します。`request_readback` はコピーとマップを開始し、`finish_readback` は完了を待って密な RGBA8 を返します。要求はバッファとデバイスを所有し、表示インスタンスを破棄しても `Readback::wait_ready` で完了を処理できます。要求を途中で捨てても、GPU のコピー完了までは予算の予約を保持します。更新のないフレームでも `poll` を呼んで完了通知を処理できます。

表示の世代が変わった要求、別の表示インスタンスの要求は採用しません。`reset` は旧テクスチャを参照するコピーの完了を待ってから資源を手放し、旧資源の分を次世代の予算として二重に使うことを防ぎます。GPU の確保・実行失敗では古い表示を無効にし、理由を返します。呼び手は既存の CPU 合成経路に戻してください。保存用の CPU データと表示用の GPU データは分離して管理してください。

### 常駐後の計測

Windows でも同じ example を使用できます。出力されるアダプター名・バックエンドと併せて記録してください。

```
cargo run --release -p yolu-gpu --example resident_measure -- 4096 3
```

引数はキャンバスの一辺（128 の倍数）と測定回数です。4 レイヤーと 16 レイヤーを測り、初回常駐と各ケース 1 回のウォームアップを除外します。局所変更は 1 レイヤーの 1 タイル、全面変更は全レイヤーの全タイルを実際に変更します。GPU 時間は入力の照合、必要な転送、合成と完了待ちを含みます。読み戻し有りでは更新範囲（局所 128²、全面 4096²）を取得します。CPU は同範囲の合成だけで、表示への転送は含めません。入力を変更する処理と画素の一致確認は計測外です。

### キャンバスの表示の更新の計測

```
cargo run --release -p yolu-gpu --example canvas_measure -- 4096 5
```

CPU の表示（変わったタイルを `composite_into` → 乗算済みへ変換 → `write_texture` → 提出と完了待ち）と、GPU の常駐の表示（`update`）を、同じデバイス・同じ変更で比べます。キャンバスの一辺と反復数を引数に、環境変数 `LAYERS`（既定 `4,16,32`）でレイヤーの数を選びます。全レイヤーが全面の文書と、下地だけが全面でほかは 4 タイルの文書を、1 タイル・16 タイル（4×4）・1 レイヤーの不透明度の変更で測り、表示の画素の一致（許し 2）も毎回確かめます。出力されるアダプター名とバックエンドを併せて記録してください。ソフトウェアの GPU（llvmpipe）、WSL のコンテナの GPU（Mesa の d3d12 経由の OpenGL）、Windows の D3D11/D3D12/Vulkan の結果を混同しないでください。

4096²、下地だけが全面でほかのレイヤーは 4 タイルの文書（描いたタイルが予算に収まる、アプリが GPU で合成する側の文書）の中央値（ミリ秒、CPU / GPU）。CPU は 32 スレッドの PC でも 1 タイルずつ順に合成するので、同じ式です。

| 初めて見せる | 4 | 96 / 284 | 75〜84 / 328〜376 |
| 初めて見せる | 16 | 47 / 260 | 480〜635 / 349〜1934 |

ソフトウェアの GPU では計算も CPU が行うので、GPU の道は、この表の更新で CPU の 4.4〜7.8 倍、初めて見せるときで 3.0〜5.5 倍遅く、アプリの `Auto` は使いません。実 GPU（OpenGL への変換レイヤーを通した値）では、この条件の更新（1 タイル・16 タイル・不透明度の変更）は GPU と CPU が同じ程度で、GPU/CPU は 0.8〜1.7 倍の間で揺れます。初めて見せるときは 4 レイヤーで GPU が 4 倍ほど遅くなります。測った範囲に GPU が CPU より明らかに速い条件はありませんでした。Windows のネイティブの D3D12・Vulkan の値ではないので、実機の `canvas_measure` の結果で `Auto` の選び方を決めてください。今の `Auto` は、ソフトウェアのアダプターでなければ GPU を選びます。遅いと感じる PC では、環境変数 `YOLUPAINTER_CANVAS=cpu` か設定の「表示の合成」で CPU に戻せます。4096² で全面に描いたレイヤーが 4 枚以上ある文書は、全タイルを常駐できず（予算 512 MiB）、レイヤーの不透明度の変更のたびに全タイルを上げ直す（全面の 4 レイヤーと 16 レイヤーで、実 GPU は CPU の 2.3〜3.5 倍、ソフトウェアの GPU は 4.5 倍ほどの時間がかかりました）ので、アプリは CPU で合成します。

## メッシュマップの GPU ベイク

`BakeGpu` は `yolu-core::mesh_maps` のメッシュマップ（ワールド法線・位置・AO・曲率・厚み・接空間法線・ハイト・ID・ベントノーマル・不透明度）を wgpu の compute で焼きます。式の正本は CPU の `bake` です。準備（受け手の選別・BVH・曲率・高ポリの投影・接空間・ID・光線の方向列）と後始末（余白・記録・由来）は core の `MeshBakePlan` をそのまま使い、行ごとの計算（UV の所有者の判定・投影・各マップの値・光線）だけを WGSL で行います。GPU 側に別の式は持ちません。

```rust
use yolu_core::mesh_maps::MeshBakeBudget;
use yolu_gpu::{bake_mesh_maps, BakeBackend, GpuBakeSlot};
# fn demo(input: &yolu_core::mesh_maps::MeshBakeInput, settings: &yolu_core::mesh_maps::MeshBakeSettings) {
let slot = GpuBakeSlot::default(); // デバイスとシェーダーを使い回す（別のスレッドから共有できる）
let (result, run) = bake_mesh_maps(
    BakeBackend::Auto, &slot, input, settings, &MeshBakeBudget::default(), None, None, |_, _| true,
).unwrap();
// run.gpu: 使ったアダプターと計測。CPU で焼いたときは run.fallback_kind / run.fallback_reason が理由。
# let _ = (result, run); }
```

- **場所の選び方**: `Auto` は使えるハードウェアの GPU があれば GPU、なければ CPU。ソフトウェアの描画（llvmpipe・WARP など）は CPU のマルチスレッドより遅いので自動では使いません。`Gpu` はソフトウェアの描画も許し、使えなければ理由つきで CPU に戻ります。`Cpu` は core の `bake` です。
- **光線を飛ばすマップ**（AO・厚み・ベントノーマル・高ポリからの投影）: BVH（core の `MeshRayBvh` を平らにした配列）を compute でたどります。どの GPU でも動きます。wgpu の実験機能 ray query（ハードウェアの光線追跡。RT コア）が使えるアダプターでは、加速構造（BLAS/TLAS）を作って ray query でたどる道を**既定で使います**（`GpuBakeOptions::ray_query`。環境変数 `YOLUPAINTER_BAKE_RAY_QUERY` が `0`・`false`・`off`・`no` だと既定が切になり、アプリは設定の「ベイクで RT コアを使う」で切り替えます。`GpuBakeSlot::set_ray_query` で後から変えると、次の確認・ベイクでデバイスを作り直します）。ray query の道は、同じ光線 4096 本を compute の道と ray query の道の両方で飛ばして、当たったか・距離・三角形・重心座標を比べる自己照合に通ったときだけ使い、通らなければ compute に戻ります。アダプターが対応していない・デバイスを ray query つきで作れない・シェーダーや加速構造を作れない・自己照合に通らない、のどこで戻ったかと理由は、`GpuBakeStats::ray_query_note` に残ります（使った道は `GpuBakeStats::method`）。裏面を飛ばす設定のときは、裏面を飛ばすレイも照合し、ハードウェアの表裏の規約が compute と逆なら頂点の並びを入れ替えてもう一度確かめます。**実行して確かめたのは、RTX 3050 Laptop の Vulkan と Apple M4 の Metal です**（CPU の結果との差は試験の許容の内で、compute の道より小さい）。ソフトウェアの Vulkan（llvmpipe）は ray query を持たないので、そこでは compute だけが動きます。DX12 は DXC（新しいシェーダーコンパイラー）を同梱していないので ray query が出ず、Windows ではアダプターの選びで Vulkan を先にします。実験機能のドライバーが固まったり応答なし（TDR）になった場合は、自己照合も同じ道の中で行うので compute に戻せません。そのような PC では切ってください。ray query の道で焼いている途中の失敗（デバイスの消失・完了待ちの時間切れを除く）は、ray query を止めて compute で 1 回やり直し、入切が変わるまで compute で焼きます（`RayQueryWhy::RunFailed`）。取消・時間切れ・進捗の中止は、加速構造の構築と自己照合の間も見ます。使わなかった理由の種類は `GpuBakeStats::ray_query_why`、詳しい文（自己照合の数を含む）は `ray_query_note` にあります。光線の要らないマップは UV 空間でテクセルごとに計算します。
- **資源の決まり**: 入力の配列は読み取り専用で、出力は別のバッファです（同じバッファを読みながら書きません）。入力・出力・読み戻しの合計は既定 768 MiB の予算に収め、出力が入らない大きさは行の帯に分けて焼きます（入力の配列が入らない・1 行も入らないときは理由を返します）。1 回の dispatch は時間で大きさを合わせ（既定の目標 50 ms）、Windows の GPU の応答なし（TDR）を避けます。読み戻しは帯ごとに完了を待って渡します。取消・時間切れ・進捗の中止は dispatch の合間に見て、CPU と同じ空の結果を返します（既存のマップを変えません）。
- **CPU に戻る条件**: GPU が無い・デバイスの作成に失敗・シェーダーを作れない（`FallbackKind::Unavailable`）、予算かデバイスの上限を超える（`Budget`）、実行中の失敗（デバイスの消失・待ち時間切れ・検証エラー・量子化の前に数えた NaN・無限大・範囲外の値。`Failed`）。NaN・無限大は GPU が作った場合に数えるので、GPU の f32 では桁あふれするが CPU の f64 では焼ける入力（極端に大きな座標など）は、理由つきで CPU に戻ります。失敗したデバイスは使い続けず、次のベイクで作り直します。設定・UV・予算・手動の ID 色など CPU も断る入力は、CPU に戻さずそのままエラーで返します。
- **結果の性質**: ベイクの結果は派生のデータで、保存してよいものです。元のモデル・マテリアル・テクスチャには触れません。

### CPU との差

全バイト一致は求めません。差の原因は 3 つです。f32 と f64 の丸め、UV の覆いの境（テクセルの中心が三角形の辺のすぐ上）の判定、光線の当たり外れ（f32 と f64 で交差の判定が分かれる光線が稀にあり、その光線 1 本でテクセルの値が 1/本数 だけ動く）。AO・厚み・ベントノーマルの光線の回転は GPU の sin/cos の精度に頼らず多項式で計算し、乱数の列は core が作った方向列をそのまま使うので、CPU と同じ光線を飛ばします。UV の覆いは三角形の原点を整数と端数に分けた局所座標で計算し、許容は 1e-6 です（core は 1e-9）。余白（padding）は帯をまたぐ隣接が要るので GPU に移さず、core の後始末（CPU）で行います。

`cargo test -p yolu-gpu --test bake -- --nocapture` が、立方体・凹凸のある立方体（頂点法線・AA 2）・高ポリからの投影・名前による対応・ID の元 4 種と手動色・複数スロットと奇数の大きさ（AA 4）で、マップごとに CPU との差を測って許し幅と比べます。値は 16 bit（0〜65535）の差です。

| マップ（高ポリへの投影なし） | 許し幅（試験の判定） | 計測した最大（llvmpipe） | 根拠 |
|---|---|---|---|
| ワールド法線・位置・曲率・ハイト・接空間法線 | 最大差 8 | 1 | 光線を飛ばさず、f32 の丸めだけ |
| 不透明度・ID | 一致（最大差 0） | 0 | 整数と 0/1 の値 |
| AO・厚み・ベントノーマル | 最大差 6%（3932）、0.5% を超えるテクセルは 0.2% 以下、5% を超えるテクセルは 0.05% 以下 | 最大 2.8%（1856）、0.5% 超が 0.012%、5% 超は 0 | 光線 32 本で 1 本の当たり外れが約 3%。差が出るのは当たり外れの分かれる光線を持つ稀なテクセルだけ |
| UV の覆い（どのテクセルを焼くか） | 食い違いは覆うテクセルの 0.1% 以下 | 0（全ケース） | 辺の上のテクセルだけが分かれうる |

高ポリへの投影があるときは、投影の光線が当たるか外れるかが f32 と f64 で分かれるテクセルが稀に出ます。そのテクセルは別の面（または外れ）の値になるので、差は 0 と 1 や別の部品の色まで大きくなります（69312 面の高ポリ・2048²・AA 1 の全 10 種で、不透明度・ID・ハイトの 5 テクセル、約 400 万テクセル中。AO で 0.0047%、曲率で 0.0001% のテクセルが 0.5% を超え、最大差は AO 32%・曲率 23%・ハイト 50%・不透明度と ID 100%）。投影ありの試験は差の大きさを抑えず、0.5% を超えるテクセルの割合を 0.2% 以下、平均差を 2 以下に抑えます。

テクセルの中心が三角形が共有する辺（四角形の対角線）の上に乗る入力では、どの三角形の面の法線を使うかで AO の光線が変わります。この揺れは CPU 同士でも UV を数 ulp ずらすだけで起きるので、試験では「GPU と CPU の食い違いが、CPU 自身の揺れの 2 倍＋8 テクセルの内」であることを確かめています（6144 テクセル中、CPU 同士 61・GPU と CPU 86）。光線を減らす（本数 16 以下）と 1 本の重みが大きくなり、最大差はその分だけ大きくなります（本数 16 で 6.1% を観測）。許し幅は本数 32 の試験の値です。

### ベイクの計測

```
cargo run --release -p yolu-gpu --example bake_measure
cargo run --release -p yolu-gpu --example bake_measure -- --triangles 70000 --size 2048 --samples 64 --runs 3
```

既定は 7 万三角形・2048²・光線 64 本で、光線の要らないマップ 7 種、光線のマップ 3 種、高ポリからの投影（低ポリ 192 面 ← 高ポリ）の全 10 種を、CPU・GPU の compute・使えるアダプターでは ray query の順に測り、使った道と CPU との差も出します。引数は `--triangles`・`--size`・`--samples`・`--aa`・`--runs`・`--software`（ソフトウェアの描画のアダプターも使う）・`--no-cpu` です。GPU の 1 回目は別に出します（パイプラインの準備を含みます）。アダプターの名前・バックエンド・CPU のスレッド数と一緒に記録してください。

Linux で、アダプターが llvmpipe（Vulkan、CPU で動くソフトウェアの描画）だけの環境で測った例です（`--runs 2 --software`。CPU は 32 スレッド、ほかに負荷のある PC で測ったので時間は揺れます）。**ソフトウェアの描画なので GPU の速さの比べにはなりません**。正しさ（CPU との差）と、dispatch の分け方・帯の数を見るための値です。ハードウェアの GPU が CPU より速いか、ray query の道が使えるかは、まだ測っていません。実機（RTX など）で `bake_measure` を回し、「使った道」に ray query が出るかと、CPU との差・時間を確かめてください（自動の既定、つまり使えるハードウェアの GPU があれば GPU は、ハードウェアでの計測がまだ無いまま決めた値です。遅い PC では焼く場所に「CPU」を選んでください）。

| 条件（69312 三角形・2048²・AA 1・光線 64 本） | CPU（中央値） | GPU compute（llvmpipe、中央値） | dispatch・帯 |
|---|---|---|---|
| 光線の要らないマップ 7 種 | 9.8 秒 | 25.3 秒 | 660 回・2 帯 |
| 光線のマップ 3 種（AO・厚み・ベントノーマル、4.8 億本） | 8.7 秒 | 44.1 秒 | 1077 回・1 帯 |
| 高ポリからの投影（低ポリ 192 面 ← 高ポリ 69312 面）、全 10 種 | 5.7 秒 | 27.9 秒 | 735 回・3 帯 |

最長の dispatch は 76〜205 ms（目標 50 ms は最初の 1 回を軽くしてから時間で調整するので、遅いアダプターでは超えることがあります）。出力が予算（768 MiB）に入らない大きさの 2048² の全マップは、2〜3 帯に分けて焼きます。

## GpuPainter の同期 API の予算と失敗

読み取り入力と出力は別バッファです。1 回の読み戻しを完了してから次の束を投入します。既定 64 MiB の GPU 作業予算には入力、メタデータ（命令の並びと調整の表）、タイルごとの画素の有無の印と命令の番号の列、出力、読み戻し、およびそれらと同量の転送用余裕を計上します。1 束のタイル数は、実行が数えるこの量が予算に収まる最大で、命令の番号の列は全部のレイヤーが描かれたタイルの最大の長さで数えます。ドライバーの内部領域、シェーダー、呼び手が保持する CPU の結果はこの予算に含めません。1 束は最大 64 タイルで、デバイスのバッファ・ディスパッチ上限も適用します。ブラシは 1 回百万ダブ以内かつ予算以内です。

読み戻しは最大 30 秒待ちます。失敗したインスタンスは次の投入を拒否し、再作成が必要です。`Compositor` は GPU の初期化または実行失敗を理由付きで CPU に切り替えます。`GpuPainter` の直接利用やブラシは `Result` のエラーを受けて core へ戻してください。

## 検証と計測

```
cargo test -p yolu-gpu -- --nocapture
cargo run -p yolu-gpu --example measure
```

アダプターまたはデバイスを取得できない場合、GPU 試験は理由を標準エラーへ出して終了します（Rust の集計では passed と表示されるため `--nocapture` の出力を確認してください）。環境変数 `YOLUPAINTER_REQUIRE_GPU` を設定すると、アダプターが無くて飛ばす試験（このクレートの試験と単体試験、yolu-app の `common::canvas_device` と、GPU で焼いたメッシュマップの保存と復元の試験）はスキップせず失敗にするので、アダプターのある環境で試験が実行されたことを確かめられます。シェーダーの不具合はスキップせず失敗します。`WGPU_BACKEND` など wgpu の環境変数でバックエンドを選択できます。

GPU を使う試験は、デバイス（wgpu の Instance・Device）を作る前に `tests/support/gpu_lease.rs` の `lease()` を呼びます。同じ実行ファイルの中の試験が、デバイスを作る・使う・捨てるのを 1 つずつにするためです（Vulkan の lavapipe では、別々のスレッドでデバイスを同時に作ると、プロセスごと SIGSEGV で落ちることがあります）。貸し出しはスレッドが終わるとき（試験が終わるとき）に放され、同じ試験がデバイスを何個作っても待ちません。

GPU と CPU の浮動小数点演算や丸めの違いにより、合成結果に差が出る場合があります。非線形モードの多段合成では前段の丸め差が増幅するため、任意のレイヤー数について最大差 1 を保証しません。保存には CPU の正本を使ってください。

同期 API 用の `measure` は 4096²・4 レイヤーでウォームアップ後に測定し、転送と読み戻し込みで CPU と比較します。性能はアダプター・バックエンド・ドライバーに依存するため、出力される環境情報と合わせて評価してください。
