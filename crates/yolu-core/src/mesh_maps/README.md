# メッシュマップ

`MeshBakeInput::new` に三角形ごとの位置・UV・スロットと任意の頂点属性を渡し、`bake` で焼く。
位置はワールドの軸・モデルルート原点の静的スナップショット、UV と出力は左下原点。
`MeshBakeSettings` は全10種類、高ポリ投影、アンチエイリアス、余白、IDの由来を指定する。

`MeshBakeBudget` のメモリ見積もりを超える入力・設定の範囲外・UVの範囲外・焼く面がない場合はエラーで、進捗を呼ぶ前に断る。
曲率の線分とUVの行帯参照は見積もりに入らず、残りの予算（`max_bytes` − 見積もり）で、準備に入ってから（進捗は "Preparing" まで）断る。
手動ID色が別のモデルのものだったときも準備の途中で断る。
時間切れ・`AtomicBool` または進捗コールバックによる取消では `maps` が空になり、既存の正本を変更しない。
進捗コールバックは呼び出し元のスレッドで走り、完了で `(1.0, "Done")` を呼ぶ（その戻り値は見ない）。
rayonの並列度を変えても画素と由来は同じ。`max_degree_of_parallelism` は上限で、0 は論理プロセッサの数、
指定は 1〜`MAX_PARALLELISM`（256。1つの行のまとまりは最大256行なので、これ以上は遊ぶだけ）に丸め、見積もりも丸めた値で数える。

`MeshBakeReport` は数と時間に加え、結果が平ら・白・欠けになる理由を `notes`（`MeshBakeNote`。`diagnostics` はその文）で返す。
並びは C# の診断と同じ: UVの重なり、UV面積0の三角形、頂点法線の由来、接線が無くUVから作った三角形（`fallback_triangles`）、
非多様体・巻きの合わない辺、高ポリに当たらなかったサンプル、IDの部品の数と色の離れ（手動色・頂点カラーなしは別の記録）、
高ポリなしの接空間法線と高さ。

`BakedMeshMap` は16 bitの正本とテクセルの由来を持つ。`to_rgba8` は表示用で、正本の代わりに保存しない。
保存は `yolu_io::mesh_map::{read, read_with_limit, write}` を使う。形式1〜3を読み、形式3で書く。
`.ylp` へは `Project::with_mesh_map`（形式7だけ。旧形式は先に `upgraded`）、取り出しは `Project::mesh_map`。
派生物を置き換えても文書と未知のエントリを保つ。

## 重なった UV のテクセルの持ち主（ベイクの優先）

同じテクセルを 2 つ以上の三角形が覆うとき、受け手の並びで先の三角形が持ち主になります（`priority.rs`。ベイクの割り当てだけが変わり、焼いた後の値の計算は変えません）。`MeshOverlapPriority` は、自動の決め方（`MeshOverlapRule`: 番号の小さい三角形・3D の面積の大きいアイランド・モデルの空間の +X の側・−X の側）と、0〜1 の外の UV のアイランドを焼かないか、手で選んだ「焼かない」「優先する」アイランド（それぞれ 4096 まで。モデルの指紋に結び付く）を持ちます。既定（番号の小さい三角形・外さない・手で選ばない）は今までと同じ並びで、焼いた値も由来の鍵もバイトまで同じです。重なったテクセルの図は `overlap.rs`（`UvOverlap`。ベイクの優先は見ない）。文書の設定は `.ylp` の正本の版 33 に保存します（`docs/YLP_FORMAT.md`）。

## 以前のマップを使ってよいかの判定

以前のマップを黙って使わないために、C# の `MeshBaker.ConditionKey` と `MeshMapProvenance.Check` を移してある。

- `condition_key(input, settings, kind, reference)` は、その条件で焼いたマップの `MeshMapProvenance::condition_key()` と同じ鍵を返す。
  MaterialAsset のIDマップの素材の識別（`material_identity`）も入力から作る。鍵が同じマップだけを使う。
- `MeshMapProvenance::check(&MeshMapExpectation)` は `Current`・`Stale`（理由の並び `MeshMapStaleReason`）・`Unverified`（モデルが無い）を返す。
  `MeshMapExpectation::for_bake` は入力と設定から「焼き直したら同じになる条件」を作る。`Current` のときだけ使う。
- C# の `MeshMapSet`（種類ごとに最後の1枚を持つ入れ物）は移していない。入れ物は呼び出し側が持つ。

## 再現と計測

- `bash tools/csharp-golden/mesh.sh`: Unity同梱のMonoで、合成メッシュの正解を作り直す（C# の元は Unity ブリッジのタグ `0.4.0`。場所は環境変数 `YOLUPAINTER_UNITY_SOURCE`）。`mesh.sh <出力先> <中身の出力先>` は
  不規則なメッシュの結果の全バイトも2つ目の場所へ書く（照合に使うのは出力先の `rough.txt` のSHA-256）。
- `cargo test -p yolu-core -p yolu-io`: 既知値、C#の正解、保存、拒否、取消、並列度、予算の照合。
- `bash tools/csharp-golden/mesh.sh bench`: C#の計測。
- `cargo run --release -p yolu-core --example mesh_bench`: Rustの同じ条件での計測。

計測モデルは自作の69,312三角形の分割立方体。2048²、8レイサンプル、4スレッド、アンチエイリアス1、余白0、高ポリなし。
マップごとの秒数は準備を含み、入力構築と保存を含まない。接空間法線・高さ・不透明度はこの条件では自己ベイクの既定値になる。
一般のモデル、高ポリ投影、64サンプルの既定設定での性能を表すものではない。計測の各行の最後の列は中身（テクセルの由来の並び +
16 bit値のリトルエンディアン）のSHA-256で、C#とRustの10種類が一致している。

## C#との一致の範囲

C#の `MeshBaker`（Unity同梱のMono）と全バイト（値・テクセルの由来・由来の記録・圧縮込み）が一致することを確かめた入力:

- 立方体の16事例（法線の元・高ポリ・名前の対応・IDの各元・手動色・複数スロット・アンチエイリアス・余白・UVの重なり・巻きの反転）。
- 不規則な座標（2進で厳密に表せない値）の格子メッシュ（432〜6,912面）と、四角形ごとに離した部品のメッシュ。
  自己ベイク、AOの裏面を飛ばす・距離で減衰しない、重ねた殻の裏面への当たり、頂点接線（一部の三角形は無し）・
  頂点法線（折れ角60度の再構築）・ケージの向き（頂点法線／平均）、名前の対応（大文字小文字・`_low`/`_high`の有無・対応なし）、
  MaterialAsset・MeshPart・UvIsland・VertexColorの高ポリありのID（部品が25以上でパレットの段が4以上）、
  複数スロットと手動色、69,312面の256²（全10種類）。並列度1と4で同じ。
- BVHは97面と不規則な1,728面で、節・三角形の並びとレイ（探索の打ち切り・裏面を飛ばす・自分の三角形を無視する）。
- IDのパレット（0〜1,000,000部品）、条件の鍵、古さの判定の状態と理由の並び、診断の並びと数値、レポートの数。

この環境のMonoはfloatの式をfloatのまま計算する（C#のソースの注釈にある「doubleで計算する」は、ここでは当てはまらない。
照合の正解に `float_sum=0` の確認を入れてあり、違う環境で作り直すと試験が気づく）。Rustのf32と同じ丸めなので、不規則な座標でも
差は出なかった。照合の入力はすべて整数のハッシュと1文1演算で作り、実モデルは使っていない。
実モデル一般、異なるOSの数学ライブラリ（`sin`・`cos`・`atan2`）の丸め、64サンプルの既定設定の性能は確かめていない。

CPU版の倍精度BVHを使う。既存の `geometry` は単精度のプレビュー用で、交差判定と分割の規則が異なる。
GPU・アプリUIはこのモジュールに依存しない。
